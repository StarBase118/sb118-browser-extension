StarBase 118 browser extension

Phase 3 — awareness

A toolbar badge fed by three sources, each one switchable off. The first thing that makes the extension worth leaving installed.

What this is

Phases 1 and 2 made the extension a faster way to reach pages you were going to reach anyway. Phase 3 is different: a number on the toolbar icon is what makes someone open the popup unprompted.

SourceWhat counts as newWhere it comes from
Announcements A human post in Discord 📣announcements Discord REST, read by the ClaudeCode bot, server-side
Sims A sim on any ship you have a placement on, that you did not write HQ Postgres, via listShipSims()
News An item in the Community News feed www.starbase118.net/feed (public RSS)

Deliberately out of scope: Discord mention counts (they need a per-user relay that doesn't exist), forum activity, and any kind of desktop or push notification. The badge is the only alert surface.

How it fits together

One new endpoint on HQ. All the state lives in your browser.

Why the aggregation is server-side

The Discord bot token decides it. An extension's code is public — anyone who installs it can read it — so a bot token can never ship inside one. Sims need HQ's database regardless. Only the RSS feed could have been fetched client-side, and splitting one source out buys nothing but a second thing that can fail.

Why there is no POST /api/me/seen

The original Phase 1 design put last-seen markers in HQ's database. That route is cancelled. Returning items instead of counts means the server needs no per-member state at all: no new table, no mutating route, no CSRF surface, no migration.

The trade, stated plainly

Badge state is per-browser and does not sync. Read an announcement on your laptop and your desktop badge still shows it. For a launcher extension that seems right — the badge is a property of "this browser I'm sitting at", not of the member. If sync is ever wanted, the endpoint doesn't change; a seen route gets added alongside it.

The announcements filter is the whole feature

The 📣announcements channel is mostly automated. Measured against the most recent 50 messages on 8 August 2026:

KindCount
Webhook posts (Dyno 29, Claude Code 7, Claude 3)39
Bot user posts (ClaudeCode)3
System messages (type: 8, member join)1
Human posts with no text body1
Genuine human announcements~4

Four real announcements across roughly two weeks. Badging all fifty would make the number meaningless within a week — which is why the filter, not the plumbing, is the part that decides whether this feature is any good.

Keep a message only when all four hold:

  1. webhook_id is absent
  2. author.bot !== true
  3. type is 0 (default) or 19 (reply)
  4. it has non-empty content, or at least one attachment or embed

The title is the first non-empty line, Markdown stripped, truncated to 90 characters on a word boundary. Mention tokens (<@…>, @everyone) come out — a badge title is not the place to re-render a ping.

Two credential facts

SB118_DISCORD_BOT_TOKEN exists in ~/.secrets.env but is not in the Ansible vault or the megatool container yet — that's part of slice 3. And there are two bots named ClaudeCode in the guild; only 1478760290161266921 matches the token. Confirm with GET /users/@me before assuming a permission grant applies to the right one.

Sims — "ships you play on"

  1. Resolve the caller's writer_id from the session.
  2. Read all their writer_ids rows — a row is a placement, so several placements means several rows. Join on the writer_id string, never writer_ids.member_id (a junk Links field).
  3. Take the distinct ship names, canonicalized.
  4. Fetch each ship's recent sims, merge, sort newest-first.
  5. Drop sims the caller wrote, as author or co-author. Nobody needs a badge for their own post.
Two deliberate divergences from the Fleet Status count rules

Part-time placements are included. Fleet Status excludes them; here a writer wants sims from every ship they actually play on.

A member on LOA with zero placements gets an empty list, not "unavailable." Having no placement is a legitimate state, not a failure — the same trap behind the /loa/[id] 500 in July.

Verify before coding

The exact predicate for "active placement" must be checked against the live writer_ids schema. awards-roster-snapshot.ts is the reference for how placement rows are read today, and it filters on is_primary only. Don't assume a status column exists on writer_ids — member status lives on members.

The endpoint

GET /api/me/notifications — Authentik session required, not staff-gated. Every member gets this.

The gate lives in the handler, because /api/me/* sits outside the middleware matcher — exactly as /api/me and /api/search/forum do. The path also goes into MEMBER_SAFE_ROUTES in the route-firewall test, which is what caught the same omission on the forum route.

unavailable is load-bearing

A source that fails or times out returns { items: [], unavailable: true } — never a bare empty list. An empty list means "we looked and there's nothing new." unavailable means "we couldn't look." Collapse the two and a Discord outage reads as a quiet fleet.

Each source gets a 4-second timeout and they run in parallel, so one slow source can't hold the other two. Announcements cache for 5 minutes and news for 10 — without that, forty members polling every quarter hour is forty identical requests to the same channel.

The badge, and turning it off

Counting

storage.local holds a last-seen timestamp per source. A source's count is however many returned items are newer than that. No marker yet means everything counts, so a fresh install shows what's genuinely recent rather than a misleading zero.

The badge shows the total across enabled sources, blank at zero, 9+ above nine. Opening the popup marks every displayed source as seen and clears it. Markers only move forward, so a slow poll can't resurrect a badge you already cleared.

Toggles

Three checkboxes on the options page, all on by default. A disabled source isn't requested at all — it drops out of the query string, so switching it off removes the work rather than hiding the number.

The first-run note

The first time the badge shows a non-zero count, the popup shows a one-time, dismissible line explaining what the number counts and that any of the three sources can be switched off, linking straight to the options page.

On the first non-zero badge, not on install — explaining a number someone hasn't seen yet is just noise.

MV3 gotcha

Service workers get terminated aggressively. Alarms survive that; in-memory variables don't. All state goes in storage.local — never a module-level variable.

Slices

Each one ships and gets verified on its own. Slices 1–3 are independent — the extension renders any source that isn't live yet as "unavailable", which is the designed degradation, not a bug.

  1. HQ endpoint — news onlyPublic source, no new credential. The smallest possible first cut of the route, the envelope, and the firewall entry.
  2. HQ endpoint — simsPlacement fan-out, canonical ship names, self-authored exclusion.
  3. HQ endpoint — announcementsNeeds the Discord bot token in the vault and the secrets role. Remember --tags secrets runs before the deploy script, which only runs --tags megatool.
  4. Extension — badgeAlarm, poll, storage markers, badge text, clear on popup open.
  5. Extension — toggles and the first-run noteOptions checkboxes, narrowing the request, the one-time explainer.

Still open

  • Badge colour — take it from the SB118 brand reference, don't invent one.
  • The writer_ids active-placement predicate — verify against the live schema before slice 2.
  • The 15-minute poll interval — a guess balancing freshness against Discord's rate limits. Worth revisiting after the pilot; it's one constant.
