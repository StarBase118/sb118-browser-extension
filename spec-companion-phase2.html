StarBase 118 · Browser extension

Phase 2 — federated search

One box that both takes you somewhere in HQ and finds things across the wiki, the main site, the sim archive, and the staff forum.

Date 26 July 2026 Status Design approved · spec review passed Phase 1 Shipped 24 July

Phase 1 shipped the launcher and put a search box in the popup — greyed out. Phase 2 turns it on. The design goal was that the fast, always-useful thing (jumping to a page you have access to) never waits on a network request, and that nothing a member cannot open ever shows up in their results.

How it works

Four sources, three network calls. Each group renders the moment it lands — a slow forum query never holds up wiki results.

instant

Destinations

Type “vote”, get Votes, Voting guide, Vote archive. Matched locally against the page list HQ already sent, so there is no request at all.

public

Wiki

MediaWiki's own search, queried straight from the extension. Verified working anonymously — no auth, no new backend.

public

Main site

Community news, site pages, and the sim archive as three separate groups. One new public route on the Payload site.

staff

Staff forum

Queried through HQ rather than directly, so the staff gate is enforced on the server and results are already scoped to that person.

The sim archive came free

The original design deferred sim search until the Aria migration landed. It has landed — sims are already searchable on the main site, running on Postgres. That deferral was stale, so the biggest body of content SB118 has is in scope from day one.

The one real decision

Everything else follows from how the private source gets queried. Two options were on the table, and the trade-off is about where the staff gate lives.

Extension queries Discourse directly

  • Depends on the forum session cookie riding along on a cross-site request — behaves differently in Chrome and Firefox
  • The staff gate becomes a decision the client makes
  • Needs a spike before we can even plan it

HQ queries Discourse on your behalf ✓

  • No cookie involved, so both browsers behave identically
  • The server returns nothing to a non-staff caller, whatever the client does
  • HQ already holds the forum credentials and already reaches it internally

A correction worth recording

An earlier read of this held that Discourse's missing CORS headers made a direct fetch impossible. That was wrong — an extension bypasses CORS for hosts in its permissions, which is exactly how Phase 1's fetch to HQ worked. CORS is not why we proxy. The three reasons above are, and they hold up on their own.

What gets built on the server

1. /api/me gains a page list

Each member's response carries the HQ pages they are allowed to see. The extension caches it and matches against it locally.

The filter must reuse the same path-matching the middleware already uses. HQ's route gating defaults to open, and a second, hand-written matcher is the single most likely way this feature would list a page someone cannot open. The cache is also cleared whenever the session is not authenticated, so signing out cannot leave yesterday's page list sitting in the popup.

2. New forum search route on HQ

Staff only. It finds the caller's forum account by email — both systems provision from Authentik, so they match — then asks Discourse for results as that person, which means the scoping is Discourse's own rather than something we reimplement. Everyone else gets an empty response, not an error.

3. New search route on the main site

Public. Returns news, pages, and sims. Posts and pages come from Payload; sims reuse the search function already powering /sims/search.

How it behaves

SituationWhat happens
You type one characterDestinations match immediately; network sources wait for a second character so a single keystroke never fires three requests
You keep typingIn-flight requests are cancelled, so a slow answer to an old query can't overwrite a newer one
The wiki is slow or downThat group alone says unavailable after 5 seconds. Everything else still renders
You're signed outWiki, news, pages and sims all still work. Destinations and forum are simply absent, with a quiet sign-in line
You're not staffThe forum group never appears, and the server would return nothing even if it were asked
You press Ctrl+Shift+SPopup opens with the search box focused

Four tracks, shipped independently

Phase 2 is a label for this body of work, not a release bundle. Nothing waits for everything else.

1

HQ (megatool)

The page list and the forum route. This is the prerequisite for the most valuable group and carries the only real access-control risk in the phase — so it's the first plan.

2

Main site

The public search route. Independent of track 1.

3

Extension

The search UI itself. Works against whichever routes exist, degrading per-source for those that don't — so it can start before the others finish.

4

Making the repo public

History audit first, then license, issue templates for bugs and feature ideas, README with install instructions, docs, and tagged releases carrying both browser builds. Shares no code with the rest — a search bug shouldn't hold this up, and vice versa.

What we test

Most of the test surface is ordinary, but two cases are the ones that would actually leak something, so they're called out explicitly in the spec:

  • A plain member with no staff groups gets only their own pages back from /api/me
  • The forum route returns nothing to a non-staff caller — asserted against the route directly, so the client's own gating isn't what makes the test pass

Beyond that: result normalization per source, the cancel-on-new-keystroke behavior, per-source failure isolation, and a two-browser smoke test signed in and signed out. That last one also clears the Firefox check left open from Phase 1.

Still open

  • Store accounts — Chrome Web Store, Edge and AMO should publish under a dedicated SB118 developer account rather than a personal one. Carried over from Phase 1. Blocks store publication, but not the public repo or install-from-source.
  • Ship wiki URL — still empty in /api/me; unrelated to search, still open from Phase 1.

Deliberately not in Phase 2: the open-vote notification badge. It's cheap — HQ already knows who's eligible and who hasn't voted — and it's the first slice of Phase 3.
