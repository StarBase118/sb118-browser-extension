Verdict

Split the popup into two tabs — Launcher and New for you — and open on whichever one has something to say. That gives Jalana her pinned links back on every quiet day without burying the notification list Lhandon asked for two weeks ago. Separately, remember which notification rows a member has clicked and stop showing them, which is what Isara asked for. Both are contained changes to the popup and three library modules; no HQ change, no new permissions, no new network call. Ships as v0.4.0.

Reading the code to write this turned up three problems the feedback did not mention, and they are the reason this is a spec rather than a patch: the notification list has no upper bound on new items, a naive click-tracking write would have been silently lost most of the time, and a naive prune would un-click everything whenever a source had an outage. All three are addressed below.

The layout change

Jalana's “50 new things” is not hypothetical. LIST_CAP = 8 exists, but reading buildNotificationList() shows it only ever trims items the member has already seen — the partition is deliberate, so that slicing a time-sorted list can never drop an unread item to make room for a read one. The consequence nobody wrote down is that the fresh half is uncapped. Fifty new items render fifty rows.

Why not just move it to the bottom? That was Jalana's other suggestion and it is the smallest possible diff. It was rejected because the badge would then point at something you have to scroll to find, which is most of what Phase 3.1 was for. Capping the section's height and scrolling inside it was also considered: it bounds the damage without removing it, since Jalana still scrolls past a section she did not come for, on every open.

The marker gate

Splitting the popup into panels separates two things that used to be the same event: rendering the notification list, and the member seeing it. Today advanceLastSeen() runs at the end of renderNotifications(), which is correct only because there was nowhere for the list to hide.

With tabs, the panel renders on every open including opens that land on Launcher. Left alone, that clears the badge for a member who never looked — silently, and losing information. So the advance moves into showNotifs(), the one function that makes the panel visible.

Decided

“Seen” means the panel was on screen. A source's marker advances to the newest item in the payload it was showing, and the display cap does not enter into it.

This also closes the advanceLastSeen entry in the repo's housekeeping backlog, which had been left alone pending exactly this call.

An honest note: under the default-tab rule, this gate never actually fires. The panel is hidden at open only when the cached count is zero, which means nothing in the payload is newer than its marker, which means the advance it skips would have been a no-op anyway. The two decisions happen to make each other safe.

That coincidence is the argument for the move, not against it. Leaving the advance in renderNotifications() makes the marker's correctness depend on a rule living in a different function — one that nothing states and no test protects. The first change to the default-tab rule breaks it without a sound.

The click that never landed

The obvious way to record a click is to call the storage write and let it run. It would have failed most of the time.

openUrl() calls browser.tabs.create() and then window.close() on the same synchronous turn. Recording a click is a read-modify-write: its set is only issued after its get resolves, by which point the popup context is gone. The write is dropped — silently, and precisely on the feature the phase exists to deliver.

src/popup/popup.ts — the notification row's click handler
- a.addEventListener('click', (e) => {
- e.preventDefault()
- openUrl(item.url) // tabs.create() then window.close()
- })
+ a.addEventListener('click', async (e) => {
+ e.preventDefault()
+ // Tab first: the member's navigation must not wait on bookkeeping.
+ browser.tabs.create({ url: item.url })
+ // Then the write, AWAITED — window.close() destroys this context,
+ // and a read-modify-write started but not finished here never lands.
+ await addClicked(clickedKey(item.source, item.id)).catch(() => {})
+ window.close()
+ })

Opening the tab first means the member sees no delay at all; only the popup's own closing waits, by a few milliseconds. Routing the write through the background worker via runtime.sendMessage would also survive teardown, and was rejected as the larger change — a new message type, a new worker handler, and a second owner for a key the popup is the only writer of.

Devtools cannot throttle extension storage, so the manual test proves this by inserting a two-second delay into the write and confirming the popup visibly hangs open — then removing the await and confirming the clicked row comes back.

The outage that un-clicks everything

The clicked-key list has to be pruned or it grows forever. The obvious prune — drop any key whose item is no longer in the payload — has a failure mode worth drawing.

GET /api/me/notifications is untouched.

What gets stored

browser.storage.local
KeyTypeNotes
notifClicked string[] New. Each entry is `${source}:${id}` — never the bare id. NotificationItem.id is only unique within a source, so a sim and a news item can both be "1234"; keying on the bare id would hide an unrelated row, rarely enough to look like a ghost.
notifItems sources Unchanged. Still the worker's cached payload, still the thing the popup renders and prunes against.
notifLastSeen Partial<Record<source, ISO>> Unchanged shape. What changes is when it is written — on panel visibility rather than on render.
notifCount number Unchanged, and deliberately not filtered by clicks. Clicking cannot outrun the marker, so filtering it would change no observable number.

Nothing here leaves the member's machine. That is a stated privacy property of the extension and the reason cross-device sync of read state is explicitly out of scope.

Decisions

Decided · 1

Two tabs, not a reorder and not a scroll cap. The launcher is whole and unpushed; the list is whole and uncapped.

Supersedes Phase 3.1 decision 4. Its reasoning — “a launcher that also reports what is new, not a notification app” — is exactly why the launcher is not the one that gets displaced.

Decided · 2

The popup opens on the tab that has something to say — New for you when the cached count is above zero, Launcher otherwise. The choice is not remembered between opens.

A badge that says 3 and a first screen that does not show the 3 is the Phase 3.1 complaint in a new costume. A first screen that depends on something the member did days ago and will not remember doing is worse than one that depends on today.

Decided · 3

Tab switching toggles visibility and never re-renders.

Load-bearing, not an optimisation. renderNotifications() recomputes isNew from the marker, which has already advanced by the time a tab can be clicked — so a re-render would clear every gold dot mid-visit, which is the exact failure Phase 3.1 decision 1 exists to prevent.

Decided · 4

A clicked item is filtered out of the list permanently, and the write is awaited before the popup closes.

Isara's literal request — remove it as she clicks — is unobservable, because the popup closes on that same click. What she can observe is the next open, and that is what changes.

Decided · 5

Pruning is scoped to healthy sources. A source that is absent or flagged unavailable keeps every key it has.

Deferred

Automated DOM tests for tab visibility, ARIA state, keyboard activation and the no-rerender invariant.

Every test in this repo runs against a pure module; there is no jsdom harness and standing one up is larger than either feature here. Named as a known gap rather than left unsaid — the three most load-bearing behaviours in this phase are covered by manual steps only, and manual steps rot. If a later phase touches the popup's DOM again, build the harness first.

Steps

Each names what it reuses before what it adds.

1 · The clicked set

reuses readStorage() guard pattern reuses notifications-store.ts adds notifClicked + get / add / prune

2 · Filtering the list

reuses the fresh/seen partition reuses LIST_CAP backfill arithmetic adds a clicked parameter, defaulted empty adds selectDefaultTab()

Filtering happens before the partition. That is what makes a removed row backfill from the next item down rather than leave a hole.

3 · The tab strip

reuses #launcher / #results swap for search reuses badgeText() for the 9+ pill adds the strip, two panels, ARIA tablist keyboard handling

4 · Moving the marker

reuses advanceLastSeen() unchanged adds the render snapshot stash and showNotifs()

The advance runs against the snapshot renderNotifications() rendered, never a fresh storage read — otherwise a worker poll landing between render and tab click marks an item seen that was never on screen.

5 · The awaited click write

reuses browser.tabs.create() adds a handler that does not call openUrl()

6 · Mutation checks

Six deliberate breaks, each with the test that must go red: dropping the clicked filter, keying on the bare id, filtering after the partition, inverting the default-tab comparison, no-op'ing the prune, and letting the prune treat an unavailable source as healthy.

The backfill test's fixture size is load-bearing — three seen items against a cap of two is the minimum that can tell filter-before from filter-after. Do not shrink it without re-running the mutation.

Settled before planning

All three were answered by Jordan on 2026-08-28. Nothing in this spec is open.

  1. Should the v0.4.0 release notes call out that the badge now persists until you look at the list?

    Yes. One line in the release notes and in the forum reply. It is a visible behaviour change — previously any popup open cleared it — and it reads as a bug fix to anyone who noticed the old behaviour, a surprise to anyone who didn’t.

  2. Does a clicked item need any way back?

    No recovery path. Once filtered, the popup will not show it again; the member goes to Discord, HQ or the wiki as they would have anyway. Revisit only if a tester asks — adding one means a history view, which is a phase of its own.

  3. Who replies to Jalana and Isara on topic 4180, and when?

    ClaudeAI replies, after v0.4.0 is launched and live-verified — not before, per the standing rule that no fix is announced until it ships. Both replies name the person who asked, as the previous rounds did.
