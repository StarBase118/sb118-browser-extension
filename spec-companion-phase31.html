SB118 browser extension · design spec

Phase 3.1 — listing the notifications

The badge says “3”. Nothing tells you what the 3 are. This closes that, and nothing else.

Where this came from

Lhandon Nilsen, in the staff test thread, with a hand-drawn mockup attached:

I did notice that there was a notification number, just like on an app, but when I clicked it, it didn’t show me where that was.

Phase 3 shipped the badge deliberately without the list — the scope line was documented everywhere testers would look. It is now the most-asked-for thing in the test round.

Nothing changes in HQ. GET /api/me/notifications already returns every item with a title, a url and a timestamp; the worker was simply counting them and throwing them away.

The problem that had to be solved first

Opening the popup marks everything read. That was harmless when the badge was only a number — there was nothing on screen to lose. The moment items are listed, it means the “3” you clicked is already cleared by the time your eyes reach the list.

The new set is held in memory for the life of that one popup, so a re-render inside the same visit cannot make the dots disappear. Dots stay lit for the visit that revealed them, and are gone next time.

The four decisions

Chosen

New stays marked for the visit

Rather than a bare recent list, or per-source “mark read” buttons that put three headings between you and the launcher.

Chosen

Render the worker’s cache

One fetch path instead of two, no loading state, and the list can never disagree with the badge — it is the same data that produced the count.

Chosen

Always present

Hiding it once everything is read would make the feature vanish exactly when someone goes looking for it.

Chosen

Below the launcher grid

This is a launcher that also reports what’s new. Most opens are “take me to HQ”, and putting the list first pushes the pins off the bottom.

Two things deleted rather than added

Removed

The first-run explainer

It exists to explain a bare number. Once the items are on screen, the paragraph and its Dismiss button stop earning their space.

Removed

“Mark all read”

Opening the popup already marks everything read, so the button would do what had just happened.

Two real bugs the review caught

The spec went past ChatGPT three times. Two of the findings were design errors, not wording — both would have shipped.

Would have shipped
Sorting by time and slicing drops unread items

Markers are per source, so “new” is not a function of absolute time across the whole list. If the sims marker is an hour old and the news marker is three days old, then a read sim from five hours ago sorts above an unread news item from two days ago. Cap the time-sorted list at eight and the unread item is the one that falls off.

The fix is to partition new from old first, then fill the remaining slots — which also puts new items at the top, where someone who just clicked a badge expects them.

Would have shipped
The worker cannot know which snapshot you saw

The first fix stopped the worker refetching. Not enough: a worker that reads the cache when the message arrives still reads it later than the popup rendered it, and the message carries nothing saying which snapshot was on screen. An item arriving in between would be marked read without ever being displayed.

The popup already holds that snapshot and can already write storage, so it advances the marker itself. markAllSeen() is deleted outright — one writer per piece of state, and one less message type.

What the section says, in every state

Written down so the code and the tests cannot drift apart.

StateWhenShows
ItemsCache readable, items presentThe list, new ones dotted
QuietCache readable, nothing in it“Nothing new right now.”
CheckingCache absent or corrupt“Checking for updates…” and a refresh
OutageEvery enabled source failed“Couldn’t reach HQ — this list may be out of date.”
OffEvery source switched offNothing — the section is hidden

Quiet and Checking are told apart by the getter’s return value, not by how many items came back. A cache we could not read must never say “nothing new” — that is a claim we have not earned. A corrupt cache is treated exactly like a missing one, which also repairs it.

How it’s built

WorkerKeeps the payload it already fetched instead of discarding it after counting.
New pure modulebuildNotificationList() — merge, flag new, partition, cap. No I/O, no DOM.
PopupRenders rows, then advances the marker from what it just rendered.

Why the core is a pure function

The Phase 3 sims bug shipped because every unit test mocked listShipSims, so the source returned empty for every member and no test noticed. buildNotificationList takes plain data and returns plain data specifically so it can be tested against real payloads instead of a mock that drifts away from the thing it stands in for.

Ten unit tests on the builder, three on the store, and seven end-to-end checks driving the built extension in Chromium — including one that writes a newer item into the cache mid-visit and proves it is still unread on the next open.

Deliberately not in this phase

  • Any HQ change. The endpoint already returns what is needed.
  • Per-item dismissal. Read state is one timestamp per source; per-item state is a different data model.
  • Read state that syncs between browsers. Still per-browser, unchanged.
  • New sources. Announcements, sims and news only.

Known ceiling, worth stating rather than discovering: the endpoint returns at most 20 items per source, so a very busy week caps both the count and the list. That was already true of the badge.
